# Assignment 2 — Optimised Matrix Multiplication and Sparse Matrices

Big Data · ULPGC · 2026–2027

This folder contains the Java implementation, the results obtained on a Windows 11 laptop, the four plots and the report.

## Files

- `Assignment2Matrix.java`: four sequential multiplication methods (Baseline i-j-k, Reordered i-k-j, Blocked 32, and CSR×CSR) and the experiment runner.
- `summary.csv`: median, IQR, nonzero counts and approximate memory/storage for all 53 configurations.
- `raw_times.csv`: 265 original timing observations (five repetitions per configuration).
- `raw_memory.csv`: 265 approximate Java heap-delta observations.
- `measurements_with_context.csv`: derived join of the 265 paired observations, including numeric type, one algorithm worker thread, and observed input densities. This file does not replace the original raw exports.
- `make_measurements_table.py`: reproduces the derived joined CSV from the untouched raw files.
- `plot_requirements.txt`: versions tested when generating the supplied plots.
- `Experiment_Setup.txt`: configuration recorded by the program on the student's laptop.
- `plot_results.py`: creates `fig1_dense_time.png` through `fig4_storage_estimate.png`.
- `Assignment02_Report.pdf`: English report (six pages).

## Run on Windows (Java 21)

Open PowerShell or the IntelliJ terminal in the folder containing `Assignment2Matrix.java`:

```powershell
javac Assignment2Matrix.java
java Assignment2Matrix
```

The program runs its correctness tests and writes four new files to `results_assignment2/`:
`summary.csv`, `raw_times.csv`, `raw_memory.csv`, `Experiment_Setup.txt`.

The new numbers will depend on the machine and runtime state. They should not be substituted for the submitted laptop measurements unless the experiment is deliberately repeated and the report is updated.

## Recreate the figures

Requires Python 3 and packages pandas, numpy, matplotlib:

```powershell
python -m pip install -r plot_requirements.txt

```

The plotted versions were generated with Python packages listed in `plot_requirements.txt` (in the reporting environment, not measured on the Windows JVM laptop). The plotting script reads the supplied `summary.csv` from its own folder. To make plots from a new experiment, copy the new `results_assignment2/summary.csv` to this folder first, retaining the old version separately.

## Input and comparisons

- Dense sizes n = 20, 40, 80, 120, 160, 200, 320.
- Sparse sizes n = 80, 160, 240, 320 and zero percentages = 50%, 80%, 95%, 99%.
- The matrices are generated by Java `Random` with the seed `20261029 + 1009*n + 7919*sparsity`; use sparsity `-1` for dense tests.
- The dense generator draws integers 0–9. The sparse generator chooses zeros with the requested target probability and nonzero values 1–9. Actual nonzero counts are included in the CSV.
- Dense comparisons use equivalent `long[][]` inputs and output. CSR inputs are converted before the timed kernel; CSR output is retained as CSR during timing.
- Timing uses `System.nanoTime()`, two warm-up runs and five measured runs; output allocation is included, input generation and conversion are not.
- IQR in the CSV is calculated from the sorted 5 observations as the difference between the 4th and the 2nd observations (zero-based indices 3 and 1).
- Each method is checked against the baseline; small known, identity and zero cases are also checked.

## Raw columns and labels

The original CSVs were copied byte-for-byte from `Experiment_Setup.zip` created on the laptop. They contain all 265 original time observations and 265 memory observations. The supplementary `measurements_with_context.csv` combines those measurements and records the data type (`long`, 64-bit), sequential algorithm worker count (1), actual observed nonzero proportions for both inputs, and output representation per observation. To rebuild it, run `python make_measurements_table.py`.

The field `density_pct` in the **original** CSVs is a target/configuration label, not always the measured share of nonzeros. In `dense` tests it is 100% as a dense **storage** label, even though inputs drawn from 0–9 contain approximately 10% zeros. In `sparse_compare`, it is 100 minus the target percentage of zeros. Measured densities can be calculated as `100*nnz_a/(n*n)` and `100*nnz_b/(n*n)` and are provided in the context table.

All methods multiply sequentially on one application worker thread; this is not a statement about internal JVM GC/JIT threads. The Java implementation uses no third-party libraries and was run with standard IntelliJ/JDK 21 settings (no explicit JVM tuning flags recorded). `javac` in the README uses default compiler options.

## Memory limitations

`raw_memory.csv` records the difference between JVM heap use immediately before and after the multiplication, with a GC request before the run. It is **not** peak resident set size. This number is sensitive to temporary allocations and garbage collection.

The estimated numeric array payload assumes 8 bytes per `long` and 4 bytes per CSR index. It does not include object overhead, temporary `ArrayList`/boxed objects, spare capacity or total JVM usage. It should not be presented as measured RAM use.

## Environment and reproducibility

The experiment ran on the same Windows 11 laptop as Assignment 1. The previously recorded hardware is an **Intel Core i5-10210U**, with **4 physical cores**, **8 logical processors** and **7.72 GiB RAM**. Assignment 2 itself recorded Java 21, Windows 11 and eight available logical processors; the CPU, physical cores and RAM are reused from the earlier hardware log, not newly measured. The earlier baseline and environment are documented in https://github.com/marcelakuczynska/BigData-Assignment1 .

Maximum completed matrix size: 320 × 320. The code is sequential and creates no explicit worker threads. It does not include full-application timing or conversion time. The preparation-stage program included planning thresholds of 10 seconds per multiplication and 512 MiB memory, but the later simplified version run on the laptop did **not enforce** either limit. Consequently, no claim is made that peak process memory was verified against 512 MiB. The largest attempted and successfully completed size was n=320; there are no recorded timeouts or allocation failures. This is a protocol limitation, not a reason to discard the genuine measurements.
